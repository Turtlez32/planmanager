Overview

A Vercel-hosted MCP server that stores, retrieves, and serves HTML plan documents created by AI agents. Claude and Codex connect to it via the Model Context Protocol and call tools to create, update, and list plans. Each plan gets a public slug URL that any browser or agent can read with no auth. No REST API. No dashboard. No VPS. No Docker.

How it works: An agent starts a project, calls create_plan with the HTML content, and gets back a public URL (plans.turtlez.au/p/<slug>). Any other agent or browser can fetch that URL at any time. Updates go through update_plan. The owner manages plans by asking Claude — no web dashboard needed.
Auth model: Each agent has a unique bearer token configured in their MCP client settings. The server identifies the agent from the token (claude or codex) and records it on the plan. No API key management UI. No JWT login. Tokens live in agent config only.

Database Schema

One table. No users. No API keys. Agent identity comes from the MCP token at request time.

plans

id SERIAL PK auto-increment
slug TEXT UNIQUE 8-char random alphanumeric — used in public URL
title TEXT NOT NULL human-readable plan title
description TEXT short summary
tags TEXT comma-separated, e.g. "react,auth,api"
blob_url TEXT NOT NULL Vercel Blob URL where the HTML file lives
created_by TEXT NOT NULL 'claude' or 'codex' — resolved from MCP token at write time
created_at TIMESTAMPTZ DEFAULT NOW()
updated_at TIMESTAMPTZ set manually on every update
Search: For a personal tool at this scale, ILIKE '%term%' on title, description, and tags is sufficient. No FTS extension needed.

MCP Tools Reference

All tools require a valid Authorization: Bearer <token> header. The token resolves to an agent name (claude or codex) which is recorded on write operations.

create_plan claude · codex
Creates a new plan. Stores HTML in Vercel Blob, saves metadata to Postgres.
Input: { title: string, description: string, tags: string, html: string }
Returns: { slug, url: "https://plans.turtlez.au/p/<slug>", created_by }
update_plan claude · codex
Replaces the HTML for an existing plan. Optionally updates description and tags. Sets updated_at.
Input: { slug: string, html: string, description?: string, tags?: string }
Returns: { slug, url, updated_at }
get_plan claude · codex
Fetches plan metadata. HTML is available at the public URL — agents should fetch it directly from there.
Input: { slug: string }
Returns: { slug, title, description, tags, url, created_by, created_at, updated_at }
list_plans claude · codex
Lists all plans, newest first. Optional search filter across title, description, and tags.
Input: { search?: string, tag?: string, limit?: number }
Returns: [ { slug, title, description, tags, url, created_by, updated_at } ]
delete_plan claude · codex
Deletes the Blob file and removes the Postgres row.
Input: { slug: string }
Returns: { deleted: true, slug }

Auth Model

Token Resolution

MCP_TOKEN_CLAUDE env var 32-byte hex token → resolves to agent name "claude"
MCP_TOKEN_CODEX env var 32-byte hex token → resolves to agent name "codex"
How it works: The MCP request arrives with Authorization: Bearer <token>. lib/auth.ts compares the token against the two env vars using a timing-safe comparison (crypto.timingSafeEqual) and returns the agent name or throws a 401. No database lookup needed — two env var comparisons is the entire auth layer.
Token generation: Run node scripts/gen-tokens.ts once to print two random tokens. Add them to Vercel environment variables. Configure each token in the respective agent's MCP settings. Tokens are never committed to git.

Public Plan Viewer

GET /p/:slug

Auth none fully public — the slug is the access token
Handler api/p/[slug].ts looks up blob_url from Postgres, fetches from Blob, streams HTML to browser
Content-Type text/html served directly — renders in browser as-is
Routing vercel.json rewrite /p/:slug → /api/p/[slug]
Agent reading: Agents do not need MCP to read a plan. They simply fetch https://plans.turtlez.au/p/<slug> via HTTP — the HTML is returned directly. No token required. This is the shareable link.

vercel.json

{
  "rewrites": [
    { "source": "/p/:slug", "destination": "/api/p/[slug]" }
  ]
}
All other routing is handled automatically by Vercel's api/ directory convention. /api/mcp → api/mcp.ts, /api/health → api/health.ts.

Instructions for Building Agents

How to build this project

  1. Read this entire document before writing any code.
  2. Complete Phase 0 Vercel setup before writing application code — you need the env vars from Vercel Postgres and Blob before the code will work.
  3. Build phases in order: scaffold → DB layer → MCP server → viewer → deploy.
  4. TypeScript strict mode throughout. No any types.
  5. Use @vercel/postgres for DB access and @vercel/blob for file storage — do not use raw pg or node-fetch.
  6. Auth is two env var comparisons using crypto.timingSafeEqual — nothing more complex is needed.
  7. HTML files are stored in Vercel Blob with access: 'public'. The public URL returned by Blob is stored in blob_url in Postgres.
  8. The /p/:slug route is the only public HTTP endpoint. Everything else requires a valid MCP token.
  9. There is no web dashboard. Plan management happens through MCP tool calls.
  10. After Phase 3, test the MCP server locally before deploying: vercel dev with a local .env.local.
  11. Future deploys: git push origin main — Vercel auto-builds and deploys from GitLab.
