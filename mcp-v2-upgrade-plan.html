PlanManager migration specification

MCP TypeScript SDK v2 Upgrade

A controlled migration of the Vercel-hosted MCP server and its integration tests from @modelcontextprotocol/sdk v1 to the split v2 packages, while keeping one endpoint compatible with Claude and Codex.
Prepared 2026-08-17
Status Ready to implement
Risk Low–moderate
Runtime Vercel Node.js 22
Clients Claude + Codex
Outcome Architecture Scope Phases Verification Rollback

Target outcome

Release goal: upgrade the application to stable MCP TypeScript SDK v2 without changing the public MCP URL, bearer tokens, permissions, tool names, plan ownership rules, or stored data.

The production endpoint remains POST /api/mcp. Claude and Codex continue connecting over Streamable HTTP with their existing credentials. The v2 server initially preserves legacy 2025-era behavior, then gains dual-era serving through createMcpHandler() after the basic SDK migration is proven.

Compatibility architecture

Claude ─────┐
            ├── HTTPS + Bearer token ──► /api/mcp ──► v2 MCP server factory
Codex ──────┘                                      │
                                                   ├── legacy 2025 request
                                                   └── modern 2026 request

Tool handlers ──► auth context ──► lib/plans.ts ──► Neon + Vercel Blob
Compatibility rule: configure the new handler with legacy: "stateless". Do not use legacy: "reject" until both real clients have passed production-equivalent smoke tests.
Serverless rule: keep the MCP layer stateless. Do not add an in-memory session map, resumability store, or long-lived connection for these CRUD tools.

Implementation phases

0

Baseline and safety

No behavior changes
  1. Create a dedicated migration branch from the known-good production revision.
  2. Confirm the working tree and exclude unrelated worktree changes from the upgrade commit.
  3. Record the current production deployment ID and keep it available for rollback.
  4. Run TypeScript and the existing Playwright suite; save the results as the migration baseline.
  5. Exercise all five tools against the current endpoint using both non-admin principals.
1

Add v2 dependencies alongside v1

Reversible package step
  1. Add the v2 server, client, Node adapter, and Zod packages without immediately removing v1.
  2. Add engines.node: "22.x" and confirm the Vercel project runtime agrees.
  3. Run the official codemod from the repository root on a clean tree.
  4. Search for every @mcp-codemod-error marker and review the complete generated diff.
npm install @modelcontextprotocol/server@^2.0.0 \
  @modelcontextprotocol/client@^2.0.0 \
  @modelcontextprotocol/node@^2.0.0 zod@^4.4.3

npx @modelcontextprotocol/codemod@latest v1-to-v2 .
2

Migrate tool registration and results

Primary source change
  1. Import McpServer from @modelcontextprotocol/server.
  2. Replace each variadic server.tool() call with server.registerTool().
  3. Wrap every input definition in an explicit z.object(), including z.object({}) for plan_list.
  4. Declare an output schema for create, update, delete, list, and get.
  5. Return validated structuredContent while retaining a JSON text content block for broad client compatibility.
  6. Preserve tool names, descriptions, argument names, revision conflict behavior, and ownership enforcement.
3

Preserve the existing HTTP behavior

First safe deployment
  1. Replace the v1 transport import with NodeStreamableHTTPServerTransport from @modelcontextprotocol/node.
  2. Keep sessionIdGenerator: undefined and create a fresh server and transport for every request.
  3. Keep the current bearer-token authentication before MCP request handling.
  4. Retain the current endpoint path, POST handling, and error logging.
  5. Deploy this compatibility-first version to a Vercel preview environment.
4

Migrate the integration client

Tests use v2 independently
  1. Import Client and StreamableHTTPClientTransport from @modelcontextprotocol/client.
  2. Continue sending the Authorization header through requestInit.
  3. Read structuredContent when present and verify it matches the text fallback.
  4. Keep client connections short-lived and ensure client.close() remains in finally.
  5. Run tests once with the v2 test client against current production and once against the v2 preview server.
5

Remove v1 and validate the dependency boundary

Complete SDK migration
  1. Remove @modelcontextprotocol/sdk only after all imports have moved.
  2. Search source, tests, scripts, manifests, and lockfile for unintended v1 references.
  3. Perform a clean install and confirm only the expected MCP v2 packages are present.
  4. Type-check without skipLibCheck temporarily to expose package-boundary errors; restore the project setting only after review.
rg '@modelcontextprotocol/sdk|@mcp-codemod-error' \
  api lib scripts tests package.json
npm ls @modelcontextprotocol/server @modelcontextprotocol/client \
  @modelcontextprotocol/node zod
npx tsc --noEmit
npm test
6

Adopt the dual-era handler

Vercel simplification
  1. Convert the endpoint to Vercel's Web Standard request/response signature where practical.
  2. Create the server through createMcpHandler() with legacy: "stateless".
  3. Resolve the bearer token for each request and capture the resulting auth context in that request's server factory.
  4. Confirm unauthorized requests still return HTTP 401 without exposing token details.
  5. Verify legacy and modern requests are accepted at the same endpoint.
7

Preview, client smoke tests, and production

Release gate
  1. Copy required token and storage environment variables into the Vercel preview environment.
  2. Run the complete automated suite against the preview URL.
  3. Connect Claude to the preview endpoint and complete create, get, update, list, and delete calls.
  4. Connect Codex to the same preview endpoint with its own token and repeat the smoke test.
  5. Test cross-owner update rejection, stale-revision conflict, invalid token, and admin hard delete.
  6. Promote only after both clients pass; monitor Vercel function errors and latency after release.

Release acceptance criteria

Build and protocol

  • Clean install and TypeScript compilation pass.
  • No application import references the v1 SDK.
  • Tool discovery returns all five unchanged names.
  • Every tool advertises valid input and output schemas.
  • Text and structured results describe the same data.

Clients and security

  • Claude completes the full CRUD smoke test.
  • Codex completes the full CRUD smoke test.
  • Claude and Codex retain separate ownership.
  • Invalid and absent tokens return HTTP 401.
  • Cross-owner writes and deletes remain forbidden.

Data integrity

  • No database migration is required.
  • Existing plans remain readable and editable.
  • Revision conflict detection remains effective.
  • HTML sanitization behavior remains unchanged.
  • Soft and hard deletion retain current semantics.

Vercel operations

  • Deployment uses Node.js 22.x.
  • The MCP function remains stateless.
  • No unexpected GET/SSE session is held open.
  • Function logs contain no token values.
  • Error rate and latency match the baseline.

Rollback plan

Rollback trigger: either Claude or Codex cannot initialize or call tools, authentication changes behavior, tool results fail validation, or the production MCP error rate materially increases.
  1. Immediately promote the last known-good Vercel deployment; do not rotate or modify tokens.
  2. Confirm /api/mcp resolves to the previous deployment and run one read-only call from each client.
  3. Preserve failed deployment logs and the exact client error for diagnosis.
  4. Because the upgrade has no database migration, no data rollback should be necessary.
  5. Resume with the direct v2 Node transport if the failure occurred only after adopting createMcpHandler().

Out of scope

This upgrade does not introduce OAuth, dynamic client registration, session persistence, server-to-client sampling, subscriptions, new MCP tools, schema/database changes, token rotation, a local Codex bridge, or changes to the public plan viewer. Those should be separate decisions after the SDK migration is stable.

Definition of done

Complete when: production runs only the stable MCP v2 packages; the endpoint serves legacy and modern stateless requests; Claude and Codex pass the full smoke suite with separate bearer tokens; automated tests pass; existing plans remain intact; and the previous Vercel deployment remains available for rollback through the initial observation window.
