Overview

PlanManager should become a shared planning backend with one data model and two client paths: Claude uses a remote MCP endpoint, while Codex Desktop uses a local MCP bridge process that calls the same backend over HTTPS. This avoids depending on an unverified remote-MCP registration path in Codex while still letting both agents work on the same plans.

Primary change: remove raw public HTML uploads as the source of truth. Store markdown or structured JSON, render server-side, sanitize output, and serve a locked-down viewer page.
Why this version is safer: the original plan let any valid token update or delete any plan, and it published agent-written HTML directly on your domain. This revision adds scoped auth, ownership checks, audit fields, sanitized rendering, and a concrete Codex setup path that fits the desktop app.

Security Goals

  • Never store raw long-lived secrets in chat history, repo files, or prompt text.
  • Do not serve arbitrary agent-supplied HTML or JavaScript from plans.turtlez.au.
  • Make plan ownership and write permissions explicit rather than inferred from an agent label.
  • Let Claude and Codex collaborate on the same plans without either integration becoming a single unsafe super-user.
  • Keep the public viewer shareable, but treat it as unlisted content by default, not private content.

Content Model

Source of truth

Store plans as markdown plus metadata. Optionally support a structured plan_json later, but do not make raw HTML the main authoring format.

Viewer strategy

Render markdown on the server with inline HTML disabled, sanitize the rendered output, and return it inside a controlled page shell.

If HTML import is ever needed

Treat imported HTML as a migration-only path, sanitize it through a strict allowlist, strip script, style, event handlers, iframes, forms, and unknown tags, then store the cleaned result separately.

Do not do this: accept { html: string } from an agent and serve that exact content back as public text/html under your main domain.

Authorization Model

Principals

Use explicit principals such as claude-remote, codex-desktop, and optional admin.

Scopes

Each token resolves to a principal and a scope set such as plans:read, plans:create, plans:update-own, plans:update-any, plans:delete-own, plans:delete-any.

Ownership rule

By default, both Claude and Codex can read all plans and update only plans they own. Shared-edit plans can be enabled by setting a plan flag or using a higher-scope token.

Recommended default: Claude and Codex both get read + create + update-own. Reserve delete-any or update-any for an admin-only token.

Viewer Hardening

  • Render markdown with raw HTML disabled.
  • Sanitize rendered output through a strict allowlist.
  • Set Content-Security-Policy to block scripts, objects, forms, and framing.
  • Set X-Content-Type-Options: nosniff.
  • Set Referrer-Policy: no-referrer.
  • Set X-Frame-Options: DENY or equivalent CSP frame-ancestors 'none'.

Suggested CSP

default-src 'none'; img-src 'self' https: data:; style-src 'self' 'unsafe-inline'; font-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; script-src 'none'; object-src 'none'; connect-src 'none'

Tool Surface

Shared logical actions

  • create_planInput: { title, description?, tags?, markdown, visibility? }
  • update_planInput: { slug, markdown?, description?, tags?, visibility? }
  • get_planReturns metadata plus source markdown, owner, revision, and public URL when allowed
  • list_plansSearches title, description, and tags
  • delete_planSoft delete unless admin hard-delete is explicitly requested
Claude sees these through remote MCP. Codex sees the same actions through the local bridge, which internally calls the JSON API.

Codex Configuration

Recommended Codex path: configure a local stdio MCP bridge in ~/.codex/config.toml. This is the concrete setup model visible in the current desktop environment and is safer than trying to rely on an unverified direct remote-MCP stanza.

1. Save the Codex token into Keychain

security add-generic-password -a "$USER" -s "plans-turtlez-codex" -w "<CODEX_API_TOKEN>"

2. Install the bridge locally

Place bridge/codex-planmanager-bridge.mjs somewhere stable, for example /Users/twadmin/.codex/tools/planmanager/codex-planmanager-bridge.mjs.

3. Add the bridge to ~/.codex/config.toml

[mcp_servers.planmanager]
command = "node"
args = ["/Users/twadmin/.codex/tools/planmanager/codex-planmanager-bridge.mjs"]
startup_timeout_sec = 30

[mcp_servers.planmanager.env]
PLANS_BASE_URL = "https://plans.turtlez.au"
PLANS_KEYCHAIN_SERVICE = "plans-turtlez-codex"
PLANS_KEYCHAIN_ACCOUNT = "twadmin"

4. Restart Codex Desktop

After restart, the bridge tools should be available across chats and across repos because the configuration is global to the app.

5. Bridge behavior

The bridge should read the token from Keychain at runtime, call /api/v1/plans, and expose MCP tools like create_plan, get_plan, list_plans, and update_plan to Codex.

How You Will Use It

  • In the desktop app, ask Codex to create or update a plan through the local bridge.
  • That plan is stored in PlanManager as markdown, rendered safely for browser viewing, and indexed for later retrieval.
  • Inside a repo chat, ask Codex to read the plan by slug or search term and implement the repo based on the stored plan.
  • Claude can inspect, draft, or update the same plan through the remote MCP endpoint at the same time, subject to scopes and ownership rules.

Build Phases

Phase 0Platform setup
  • Connect Vercel Postgres and Blob
    Create the storage resources and connect them to the Vercel project.
  • Generate three tokens
    Create CLAUDE_MCP_TOKEN, CODEX_API_TOKEN, and optional ADMIN_API_TOKEN.
  • Store only server-side secrets in Vercel
    Add tokens and BASE_URL as environment variables.
Phase 1Core service
  • Create strict TypeScript project
    Dependencies should include Vercel storage libs plus markdown render and sanitization libraries.
  • Build content pipeline
    Implement markdown render, sanitize, page shell, and CSP helpers in lib/content.ts.
  • Implement auth resolver
    Map tokens to principals and scopes with timing-safe comparison.
Phase 2Data and API layer
  • Create schema with ownership fields
    Add owner_principal, updated_by, visibility, revision, and deleted_at.
  • Build plan service
    Enforce scopes and ownership checks inside service methods, not only at route level.
  • Add JSON API routes for Codex bridge
    These should be the stable machine API Codex uses.
Phase 3Claude MCP
  • Expose remote MCP endpoint
    Register Claude-facing tools against the same internal plan service.
  • Return markdown-based plan payloads
    Claude should work with source markdown and metadata, not raw public HTML.
Phase 4Codex bridge
  • Write local stdio bridge
    The bridge reads Keychain, calls JSON API, and exposes MCP tools for Codex.
  • Install bridge globally for Codex Desktop
    Configure it in ~/.codex/config.toml so all chats can use it.
Phase 5Verification
  • Smoke test Claude
    Create, read, update, and list a plan through remote MCP.
  • Smoke test Codex
    Create and read the same plan from the desktop app through the local bridge.
  • Repo workflow test
    Open a repo chat in Codex, read the stored plan by slug, and implement a small scaffold from it.
  • XSS test
    Attempt markdown with inline HTML, script tags, event handlers, and javascript URLs. Confirm they are blocked or stripped.

Agent Build Notes

  • Keep the public viewer for human reading only. Agent editing should use markdown source from API or MCP.
  • Do not rely on a public page fetch as the only machine-readable plan format.
  • Prefer soft deletes first. Hard delete should require an admin path.
  • Emit audit logs with principal id, action, slug, and result, but never log full secrets.
  • If later you confirm stable direct remote-MCP support in Codex with custom headers, you can add it as an optional shortcut. It should not be the only integration path.
